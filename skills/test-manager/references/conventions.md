# Test repository conventions

Read this reference before initializing a test root, creating a suite, changing case or run schemas, or validating stored state.

## Directory contract

```text
<workspace>/.tests/
├── TESTING.md
├── SUITES.md
├── STATUS.md
├── RUNNER_PROMPT.md optional project-owned Prompt template
├── .env.local         local installed-skill path; ignored by Git
├── .gitignore
├── studio.sh          macOS/Linux Studio launcher
├── studio.cmd         Windows Studio launcher
├── <suite-slug>/
│   ├── SUITE.md
│   ├── CASES.md
│   ├── RUNS.md
│   ├── STEPS.md          optional
│   └── evidence/         optional; created when evidence is stored
└── <another-suite>/
```

The root must not contain ordinary subdirectories other than suites. A suite slug uses lowercase ASCII letters, digits, and single hyphens, starts with a letter or digit, and has no path separator. Suite IDs are the uppercase slug with hyphens preserved.

The launchers and their local configuration are operational helpers, not test authority. `TESTING.md`, suite files, and immutable Run rows remain authoritative. `TEST_MANAGER_SKILL_PATH` may be absolute or start with `~/`; other relative paths, `~user`, environment-variable references, and shell expressions are invalid. The launchers parse `.env.local` as data and never source or execute it. Do not store credentials or other secrets there.

## Authority

| File                | Role                                    | Mutation rule                   |
| ------------------- | --------------------------------------- | ------------------------------- |
| `TESTING.md`        | Test strategy and global quality policy | Human/agent authored            |
| `SUITES.md`         | Suite registry                          | Regenerated by `status --write` |
| `STATUS.md`         | Current calculated summary              | Regenerated by `status --write` |
| `RUNNER_PROMPT.md`  | Project-owned Runner Prompt presentation | Human/agent authored            |
| `<suite>/SUITE.md`  | Suite charter and gate                  | Human/agent authored            |
| `<suite>/CASES.md`  | Case specifications                     | Human/agent authored            |
| `<suite>/RUNS.md`   | Immutable run ledger                    | Append only                     |
| `<suite>/STEPS.md`  | Optional procedural detail              | Add only when justified         |
| `<suite>/evidence/` | Run-scoped evidence                     | Never store secrets             |

## Root strategy

`TESTING.md` uses frontmatter `schema: test-manager/root/v1` and records the title, status, and creation date. Its body must make these decisions explicit:

- quality objective and release decision;
- in-scope and out-of-scope products, platforms, and integrations;
- quality risks and risk owners;
- test levels and types;
- environments, builds, data creation/reset, and time-zone policy;
- entry and exit criteria;
- severity, defect workflow, waiver authority, evidence retention, and privacy;
- reporting audience and cadence.

Use `UNDEFINED` for a decision not yet made. Never invent a stakeholder, owner, deadline, environment, or waiver.

## Suite charter

`SUITE.md` uses frontmatter:

```yaml
---
schema: test-manager/suite/v1
suite: checkout
title: Checkout
risk: HIGH
state: ACTIVE
owner: UNASSIGNED
planned_start: UNPLANNED
planned_end: UNPLANNED
---
```

Allowed risk values are `CRITICAL / HIGH / MEDIUM / LOW`. Allowed suite states are `PLANNED / ACTIVE / BLOCKED / COMPLETE / RETIRED`.

`planned_start` and `planned_end` are optional ISO dates for the Suite plan. Use `UNPLANNED` when a boundary has not been agreed. Studio Timeline renders the Suite start as a neutral marker and the Suite end as the orange target marker. Existing v1 suites without these optional keys remain valid.

The body defines purpose, scope/non-goals, risk statements, requirements or business capabilities, dependencies, environment/data, entry/exit criteria, regression obligation, and known limitations.

## Case specification

Use stable IDs in the form `<SUITE-ID>-C001`, for example `CHECKOUT-C001`. IDs are never reused after retirement.

```markdown
## CHECKOUT-C001 — Submit a valid card payment

- State: READY
- Priority: P0
- Type: BUSINESS_E2E
- Requirement / Risk: PAY-R01, REQ-142
- Automation: MANUAL
- Owner: UNASSIGNED
- Planned Start: UNPLANNED
- Planned End: UNPLANNED

### Objective

Prove that an authorized payment produces exactly one order and one payment fact.

### Preconditions

- A clean cart and authorized test account exist.

### Test Data

- Data set: PAY-D01; non-production card token.

### Runner Instructions

- Use the visible checkout UI. Stop before retrying if submission status is uncertain.

### Expected Outcome

- The order and payment persist after refresh and reconcile from a second view.

### Negative Assertions

- No duplicate charge, orphan order, or silent partial success exists.

### Evidence Required

- Before/after values, final UI, order ID, payment ID, and reconciliation result.
```

Allowed case states are `DRAFT / READY / RETIRED`. Priorities are `P0 / P1 / P2 / P3`. Suggested types are `UNIT / COMPONENT / CONTRACT / API / INTEGRATION / BUSINESS_E2E / UI / ACCESSIBILITY / PERFORMANCE / SECURITY / COMPATIBILITY / RECOVERY / EXPLORATORY`; add a domain type only when it improves decisions. Automation is `MANUAL / AI_BROWSER / AUTOMATED / HYBRID / NOT_SUITABLE`.

`Planned Start` and `Planned End` are optional ISO dates used by Studio Timeline. Use `UNPLANNED` when no schedule has been agreed. Case and Suite dates are planning metadata, not execution evidence.

A `READY` case must have a non-empty Objective, Preconditions, Test Data, Expected Outcome, Negative Assertions, and Evidence Required section. If something is genuinely not applicable, state why; do not leave a silent blank.

`Runner Instructions` is optional. Use it for execution constraints that belong to this Case: begin with the concrete surface or tool, then state safety boundaries, evaluator order, comparison targets, evidence discipline, and stop conditions in a few short commands. It is not a fixed click path. Test Manager core renders it through the test root's optional `RUNNER_PROMPT.md`; the full Case remains authoritative, while the project controls which fields appear in the copy-ready Prompt. Studio and exports only consume that projection. Do not persist a duplicate prompt in `CASES.md`.

## Runner Prompt template

`RUNNER_PROMPT.md` is optional for existing roots and created by `init` for new roots. When absent, Test Manager uses its product-neutral bundled default. A project template may use:

- Case identity and labels: `{{Case ID}}`, `{{Title}}`, `{{State}}`, `{{Priority}}`, `{{Type}}`, `{{Automation}}`, `{{Owner}}`, plus labels present on every rendered Case.
- Case sections: `{{Objective}}`, `{{Preconditions}}`, `{{Test Data}}`, `{{Runner Instructions}}`, `{{Expected Outcome}}`, `{{Negative Assertions}}`, and `{{Evidence Required}}`.
- Filters: `| raw` (default), `| unbullet` (remove bullet markers and preserve lines), `| compact` (remove bullet markers and join lines), and `| first` (first meaningful line).

Unknown placeholders, unknown filters, unclosed placeholders, symlinks, and non-regular template files invalidate the test root. Keep product URLs, system names, tool sequence, comparison wording, and return format in the project template or Case instructions—not in Test Manager core.

Test Manager defines no execution-profile registry. Put specialized execution rules, output fields,
trace requirements, or measurements in the project-owned `RUNNER_PROMPT.md` or Case-level Runner
Instructions. Use an independent skill when the requested method has its own methodology and output
contract; Test Manager remains responsible only for Case authority, evidence links, Run results, and
quality gates.

## Runner instructions versus optional steps

Prefer `Runner Instructions` when the runner needs guidance without freezing one navigation path. This is the normal handoff mechanism for human testers and browser agents.

Create `STEPS.md` from the provided asset only when the decision rule in `SKILL.md` is met. Each case with steps has a heading matching its Case ID:

```markdown
## CHECKOUT-C001

Why steps are required: controlled financial sequence.

|   # | Actor  | Action                 | Expected observation                |
| --: | ------ | ---------------------- | ----------------------------------- |
|   1 | Tester | Open the prepared cart | Correct items and total are visible |
```

Steps describe observable user actions and checkpoints. Put reusable setup in `SUITE.md`; do not embed CSS selectors, coordinates, implementation calls, or copied login steps.

## Run ledger

`RUNS.md` contains this exact table shape:

```markdown
| Run ID | Case ID | Environment | Build | Data | Result | Evidence | Defect / Blocker | Executed At | Executor |
| ------ | ------- | ----------- | ----- | ---- | ------ | -------- | ---------------- | ----------- | -------- |
```

Use a unique Run ID such as `20260828T153000Z-CHECKOUT-C001-R1`. `Executed At` is RFC 3339 UTC. Result is one of:

| Result    | Meaning                                                                      | Required attachment                                  |
| --------- | ---------------------------------------------------------------------------- | ---------------------------------------------------- |
| `PASS`    | Expected and negative assertions are supported                               | Evidence path or durable URL                         |
| `FAIL`    | Product behavior violates an assertion                                       | Evidence plus defect ID or explicit triage reference |
| `BLOCKED` | Execution cannot reach a valid conclusion                                    | Blocker reason or issue ID                           |
| `SKIPPED` | An authorized scope decision excluded this run                               | Reason or waiver ID                                  |
| `INVALID` | Wrong data, build, environment, permission, or procedure invalidated the run | Invalidity reason; does not count as executed        |

Use `—` only where a field is genuinely not applicable. Never overwrite an earlier row to reflect a retest. Link the new run or defect history instead.

## Evidence

Prefer paths below `<suite>/evidence/<run-id>/` using:

```text
<run-id>_<case-id>_<before|action|after|downstream|trace>.<png|mp4|json|md|txt>
```

Evidence must be sufficient to reproduce the judgment, not an indiscriminate dump. Record object IDs and source context. Redact credentials, access tokens, personal data, payment data, and unrelated records.

## Traceability

Every critical risk or required capability needs at least one ready case and, before release, a valid current run. One case may cover multiple risks, but each mapping must be explicit. Coverage is unsupported when it relies only on case titles, source-code existence, closed defects, or historical runs against a different build.
