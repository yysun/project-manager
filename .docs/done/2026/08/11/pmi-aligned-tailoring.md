# PMI-Aligned Tailoring and Schema-Only PMI Modules

## Summary

- Added `PROJECT.md` schema version 2 with a required, declare-only `tailoring` block covering the ten
  PMBOK 6 knowledge areas. Tailoring out an area requires a rationale; applying one never requires
  content. This is what makes an omission PMI-compliant — a recorded decision rather than a gap.
- Kept `PROJECT.md` v1 exactly as it was. It rejects `tailoring`, needs no migration, and reports
  tailoring as explicitly undeclared instead of implying every area is applied.
- Added five optional collection modules — `ASSUMPTIONS.md` (`ASM-`), `ISSUES.md` (`ISS-`),
  `STAKEHOLDERS.md` (`STK-`), `LESSONS.md` (`LES-`), `CLOSURE.md` (`CLO-`) — through the existing
  `{configured, items}` path, each fail-closed on its own schema once present.
- Added `RISKS.md` schema version 2 with PMI response strategy, threat/opportunity direction, trigger,
  and residual risk. Strategies are constrained to the direction, so an opportunity cannot be
  "mitigated". V1 rejects the new fields and keeps its exact normalized shape.
- Made the declaration unfalsifiable: configuring `RISKS.md` while risk is tailored out, or
  `STAKEHOLDERS.md` while stakeholder is tailored out, fails validation `TAILORING_CONTRADICTION`.
- Bound closure acceptance to reality — an accepted project closure requires project completion, an
  accepted milestone closure requires that milestone complete, and acceptance requires an acceptor, a
  date, and evidence.
- Preserved the hash-stability invariant: unconfigured modules contribute `undefined`, which canonical
  JSON omits, so installing this capability cannot stale any existing `STATUS.md`.
- Documented the contract across `conventions.md`, `init.md`, `report.md`, `review.md`, and `SKILL.md`
  (1.2.0 → 1.3.0), and stated PMI alignment accurately in the README as principles-aligned with
  documented tailoring, explicitly not certification.

## Notes

- Three existing test assertions were updated, not weakened: the `validateData().modules` map, the
  `statusData`/`reportData` schema version (2 → 3), and the CLI output key lists. These assert the exact
  output contract that this change intentionally extended and versioned; no test intent changed.
- `skills/project-manager/scripts/project-manager-studio.js` is a committed build artifact and was
  regenerated by the build; its diff tracks the library change.
- `demo/pm-studio-demo` cannot be loaded on this machine — its stored Task Contract binds an absolute
  executor root that does not exist here. This is pre-existing and reproduces identically on the
  unmodified baseline; it is unrelated to this change and was not addressed.
- Deliberately out of scope and still absent: `COST.md`, Earned Value, `TASKS.md` v4 estimates, typed
  dependencies, float and critical path, and Studio panels for the new modules. Projects that need cost
  or procurement should tailor them out with a rationale naming where they are managed instead.
- The `schedule` knowledge area is intentionally not bound to `MILESTONES.md` in the anti-fiction
  cross-check, because milestones also serve scope and integration reporting; binding it would force
  incorrect declarations.
