# Generic Project Manager Skill Plan

## Goal

Deliver a folder-native, generic `project-manager` skill that keeps small projects lightweight, adds structure only when needed, coordinates any executor through durable evidence contracts, and exposes truthful deterministic project facts without assuming Git, software, or RPD.

## Current Context

- `skills/rpd/SKILL.md` is the existing software-task execution skill and must remain unchanged. Project Manager may use it only through the optional executor adapter.
- `skills/project-manager/SKILL.md` is an empty untracked placeholder with no user content to preserve.
- The “Using Codex for PM” conversation contributes stable IDs, dependency-aware priority, evidence-backed completion, deterministic calculations, source traceability, impact analysis, and management reporting.
- The “Generic PM Skill” conversation corrects the core abstraction: a project is a folder; Git/source/RPD are optional; small projects start with three files; the same skill must feel natural for software and non-software work.
- The user fixed the ownership/API boundary: Project Manager does `plan → coordinate → track → report`; RPD does `understand → implement → test → correct → verify`; their API is Task Contract → Evidence Manifest → Project State.
- Node.js v22 and Python 3 are available. The standard skill validator is `/Users/esun/.codex/skills/.system/skill-creator/scripts/quick_validate.py`.
- The public command/skill behavior is user-facing, so `.docs/tests/test-project-manager.md` is required.

## Decisions

### Core object and progressive structure

- Treat any explicitly selected folder containing `PROJECT.md` as one project object. Do not search upward for Git, infer a repository project, or inspect sibling folders. Resolve the selected folder with `realpath`; recursively reject symlinked or escaping known state paths before reads or writes.
- Support multiple project folders under one repository/workspace. An optional workspace `PROJECTS.md` is discovery-only: frontmatter is exactly `schema_version: 1`, followed by `## PROJECT-ID - name` plus one immediate fenced JSON object exactly `{\"path\":\"relative/path\"}`. Resolve paths relative to the index folder; reject absolute/empty/escaping/symlink paths, case-insensitive duplicate IDs or paths, unknown fields, stale/missing folders, and a target whose `PROJECT.md` ID differs. Index validation and lookup never make the index project state, and ordinary project commands never read it. Moving a project folder does not change its identity, and selecting one never loads another.
- Require only:
  - `PROJECT.md`: project identity, objective, success criteria, ownership, dates, status, current milestone, enabled adapters, and structural profile.
  - `TASKS.md`: compact, machine-readable task records plus optional narrative.
  - `STATUS.md`: derived current snapshot; never the source of task truth.
- Add optional modules only when used: `MILESTONES.md`, `RISKS.md`, `DECISIONS.md`, `SOURCES.md`, `TRACEABILITY.md`, `CHANGES.md`, `handoffs/`, and `reports/history/`. Profiles are descriptive (`minimal|standard|controlled`), not incompatible schemas. Promotion adds modules without moving or renaming project/task IDs. V1 keeps task metadata in `TASKS.md`; automatic per-task-file migration is a non-goal.
- Git, storage systems, source code, and RPD are adapters, not core state. `PROJECT.md.adapters` is a JSON array from `human|rpd|agent|external`; `human` is always available. Enabling `rpd` allows tasks to choose it but does not make software fields mandatory.

### Machine-readable Markdown grammar

- Use strict frontmatter-lite for `PROJECT.md` and attempt artifacts: one unique, unindented `key: value` per line inside `---`; keys match `[a-z][a-z0-9_]*` and values must parse as complete single-line JSON values (strings therefore require double quotes). Reject comments, bare strings, nested YAML, block lists, aliases, tags, duplicates, trailing tokens, and multiline scalars.
- Use a common record-collection grammar for `TASKS.md` and optional `MILESTONES.md`, `RISKS.md`, `DECISIONS.md`, `SOURCES.md`, and `CHANGES.md`: frontmatter contains only `schema_version: 1`; each record begins `## ID - non-empty title`, followed immediately by one fenced `json` object; later Markdown until the next level-two heading is narrative and ignored by scripts. Reject duplicate IDs, malformed/reserved headings, multiple/missing metadata blocks, unknown fields, or unsupported versions.
- Lock safe IDs before using paths: project/task IDs match `[A-Z][A-Z0-9-]{1,63}`; success criteria `SC-[A-Z0-9-]+`; milestone `M-[A-Z0-9-]+`; risk `RISK-[A-Z0-9-]+`; decision `DEC-[A-Z0-9-]+`; source `SRC-[A-Z0-9-]+`; change `CHG-[A-Z0-9-]+`. Reject case-insensitive duplicates, `..`, leading/trailing hyphens, and IDs outside their namespace. These grammars exclude slashes, spaces, traversal, and story-unsafe punctuation.
- Lock `PROJECT.md` fields: `schema_version: 1`, safe `id`, `name`, `status` in `planning|active|on_hold|complete`, nullable `owner`, date-only nullable `start_date`/`target_date`, nullable milestone ID `current_milestone`, `profile` in `minimal|standard|controlled`, unique `adapters` array containing `human` plus optional `rpd|agent|external`, date-only `created`/`updated`. Require `## Objective` non-empty and `## Success Criteria` containing unique lines `- [SC-ID] non-empty criterion`. Project identity is the ID and state content, not absolute path. Moving a folder with no active attempts preserves all historical evidence; moving during an active attempt blocks tracking and requires a retry contract at the new location.
- Keep compact task authoring genuinely small. A record requires only non-empty `outcome` and a non-empty array of unique non-empty `acceptance` strings. Normalize omitted fields to: `status:planned`, `priority:P2`, `milestone:null`, `owner:null`, `executor:{provider:\"human\",root:null,scope:null}`, `depends_on:[]`, `blocks:[]`, `blocked_by:[]`, `sources:[]`, `success_criteria:[]`, `constraints:[]`, provider-default `evidence_requirements`, `external_refs:{}`, `critical:false`, `active_contract:null`, `last_manifest:null`, `created:null`, `updated:null`. `blocked_by` contains unique non-empty explicit-blocker strings; unfinished dependency task IDs are derived only from `depends_on`, never stored there. `blocks` is the exact reverse-link task-ID set derived from other tasks' `depends_on`. `external_refs` is display-only and never replaces the project task ID. Human root/scope are null. Other providers use `scope:absolute` with an existing absolute real directory or `scope:project` with a safe project-relative directory; project-scoped roots resolve against the selected logical root at issuance and remain portable when an inactive project moves.
- Define evidence requirements as an array of exact groups `{stage:\"implemented|verification|verified\",any_of:[\"file|command|review|artifact|approval|note|commit\"],minimum:positive integer}`. `any_of` is non-empty, unique, lexically normalized; groups are unique by `(stage,any_of)` and cumulative, so verified checks all groups and verification checks implemented+verification groups. Defaults: human `verified:any_of[approval]:1`; RPD `implemented:any_of[file,artifact]:1`, `verification:any_of[command]:1`, `verified:any_of[review]:1`; agent `implemented:any_of[artifact]:1`, `verified:any_of[review]:1`; external `verified:any_of[approval,artifact]:1`. Count only distinct main `evidence` records whose kinds match a group; an evidence record may satisfy at most one group, assigned by array order. Every acceptance item always requires at least one mapped evidence record. Acceptance mappings may reference only byte-identical records present in main `evidence`; mappings do not add to provider counts. Task `success_criteria` values must resolve to project criteria. Compute `spec_sha256` from canonical `{id,title,outcome,constraints,acceptance,success_criteria,milestone,executor,depends_on,sources,evidence_requirements,critical}`.
- Define lifecycle snapshot rules: planned/ready have no active contract; ready requires dependencies done/no blockers; immutable Task Contract issuance atomically authorizes ready → in_progress and sets active contract. Implemented/verification/verified/done require `last_manifest` to resolve to the latest legal manifest sequence for active contract. Done additionally requires a verified manifest, dependencies done, and no blockers. If a valid terminal verified manifest was stored while dependencies/blockers prevented done, `project update` revalidates that same stored manifest after the impediment clears and advances `verified → done` without accepting or creating another manifest. Source/spec change regresses state and clears active execution pointers while immutable history remains. Project complete requires all tasks done, present milestones complete, and every project SC mapped to at least one done task; otherwise completion is invalid, not merely unconfigured.

### Optional modules

- Milestone metadata is exactly `{status,target_date,forecast_date,forecast_updated,forecast_evidence,critical}` after defaults: status is `planned|active|complete`; dates are date-only or null; `forecast_evidence` is an evidence-record array; critical is boolean. Missing optionals normalize to null/empty/false. IDs use milestone namespace; task/current-milestone refs resolve. At most one active milestone; PROJECT current matches it. Complete requires assigned tasks done. Forecast fields must be all absent/null or all populated, with at least one evidence record whose result explains the declared forecast.
- Risk metadata is exactly `{status,probability,impact,mitigation,owner,milestone}` after defaults. Decision metadata is exactly `{status,decision,owner,due_date,date,affects}` after defaults. Change metadata is exactly `{date,observed_at,sources,affected_tasks,affected_milestones,reverify_tasks,reverification,risk_summary}`; `observed_at` is an RFC3339 UTC timestamp on `date`, and same-task changes cannot share it. `reverification` maps every reverify task to exact `{status:"pending|in_progress|complete",contract_id,manifest_id}`: pending IDs are null, in-progress binds a contract created strictly after the change, and complete binds that contract plus its verified manifest. Only the latest change by timestamp per task constrains current lifecycle, so later changes can regress previously reverified work without rewriting older evidence.
- Source metadata is exactly `{kind,location,role,status,version,sha256}` after defaults: kind is `document|pdf|sheet|requirement|specification|code|url|other`; location/role are non-empty strings; status is `current|superseded`; version is non-empty string/null and SHA-256 is lowercase 64-hex/null. A task source must be current. Any source whose freshness gates verified completion must have either content SHA-256 or an immutable non-empty version token; otherwise execution is allowed but verified manifest ingestion is prohibited as unverifiable.
- `TRACEABILITY.md` frontmatter has exactly the keys `schema_version: 1` and `items`, where items is an array of exact `{source_id,criterion,tasks}` objects. Criterion is a non-empty string; tasks is a unique lexically ordered array of task IDs; source/task IDs resolve; `(source_id,criterion)` pairs are unique and the item array is ordered by source ID then criterion. Reject unknown fields, empty criteria, duplicates, and unstable order. Coverage is `configured:false` when absent; when present, criterion coverage requires at least one task, and verified coverage requires every mapped task to have a current verified manifest. No traceability file means “unconfigured,” not zero coverage.
- Project success counts are independent of source traceability: `total` is the number of PROJECT success criteria; `covered` counts criteria mapped by at least one task; `verified` counts criteria for which every mapped task is done with its current verified manifest. An uncovered criterion cannot be verified. These same definitions gate project completion and all reports.
- Lock `STATUS.md` as a derived cache with frontmatter `schema_version: 1`, `project_id`, RFC3339 `generated_at`, and `source_sha256`, followed by concise Markdown. The digest covers canonical PROJECT/TASKS and present optional-module records, excluding STATUS/reports. A stale digest is a warning; STATUS is never task truth. Every successful mutation regenerates it. Saved reports use collision-safe `{yyyyMMddTHHmmss.SSSZ}-{audience}-{NN}.md` names and are never overwritten.

### Task Contract → executor → Evidence Manifest

- Generalize the boundary to every executor. Project Manager creates the contract and tracks returned evidence; the provider does the work. For RPD tasks, the adapter preserves the user's exact boundary and does not inspect or duplicate RPD internals.
- Implement canonical serialization in `scripts/lib/contracts.js`: recursively sort object keys; normalize schema-declared set arrays lexically; serialize compact UTF-8 JSON; reject unknown fields and unsupported versions. Hash canonical payloads with SHA-256.
- Evidence record v1 is exactly `{kind:\"file|command|review|artifact|approval|note|commit\",ref:string,result:string,sha256:null|64-lowercase-hex}`. File/artifact records require a hash. All strings are non-empty; no extra fields.
- Task Contract payload v1 is exactly `{schema_version:1,project:{id,root},task:{id,spec_sha256,title,outcome,constraints,acceptance,success_criteria,milestone,critical,sources,dependencies,evidence_requirements,executor},created_at}`. `root` is the real absolute project root at issuance; `created_at` is RFC3339 UTC. Constraints, acceptance, success criteria, milestone, criticality, dependencies, and evidence requirements use the normalized task shapes above. Source bindings are exact `{id,version,record_sha256,content_sha256}` objects. Contract executor is exact `{provider,scope,declared_root,root}`: declared root preserves the task representation and root is the resolved issuance directory. Hash the canonical payload; contract ID is `tc-<64hex>`. Derive RPD story and prompt only after the digest. Persist immutable `TASK-CONTRACT.md` with exact envelope and canonical payload. Reject existing paths, unknown/missing fields, prompt/hash mismatch, non-derived stories, and active-root/source drift.
- Evidence Manifest payload v1 is exactly `{schema_version:1,sequence:positive integer,contract_id,project:{id},task:{id,spec_sha256},status:\"implemented|verification|verified|blocked\",blocker:null|string,evidence:[evidence records],acceptance_evidence:{\"exact acceptance string\":[evidence records]},sources:[{path,sha256,role}],observed_at,notes:[strings]}`. `observed_at` is RFC3339 UTC; notes are non-empty strings; manifest sources use non-empty project-relative paths, lowercase SHA-256, and role. Hash canonical payload to manifest ID `em-<64hex>`. Persist `handoffs/{task}/{contract}/EVIDENCE-{sequence padded 3}.md` with exact frontmatter keys `schema_version: 1`, `manifest_id`, `payload_sha256`, `evidence_sha256`, followed immediately by `## Payload` and one fenced `json` canonical payload object. Reject unknown/missing envelope fields. Project paths are issuance metadata, not hashed identity. Source/task bindings and contract identity must match.
- Status rules: blocked requires blocker and may carry partial evidence; all other statuses require null blocker. Apply the cumulative stage algorithm exactly: implemented checks only `implemented` groups; verification checks `implemented` plus `verification` groups; verified checks all three stages plus every exact acceptance key with non-empty evidence and verifiable current sources. Arrays contain only exact evidence-record objects and reject extras.
- Manifest progression per contract is strictly none → implemented|verification|verified|blocked; implemented → verification|verified|blocked; verification → verified|blocked; verified/blocked terminal. Sequence starts 1 and increments with no gaps; status cannot repeat. Compute `evidence_sha256` over canonical `{evidence,acceptance_evidence,sources}` only and reject that fingerprint anywhere earlier in the same contract, regardless of sequence/status/time/notes. Ingestion records last manifest. Blocked retry resolves the blocker, clears active pointers, and creates a new contract; old attempts remain immutable.
- Map manifests deterministically: blocked → in_progress plus blocker; implemented → implemented; verification → verification; verified → done when dependencies remain done/no blockers, otherwise verified. Only update/track ingests manifests. Contract issuance is the sole evidence-free execution transition.
- RPD adapter: try story suffix lengths 12, 16, 32, then 64 digest hex until no unrelated story collision; reject if none is unique. Deterministically render executor prompt from project/task IDs, contract ID, story, selected execution root, the absolute TASK-CONTRACT path, its project-relative metadata path, acceptance, constraints, and evidence requirements; store its SHA-256 in the contract envelope and recompute on validation. The absolute path is presentation metadata, not hashed identity, and must be readable from the RPD process before dispatch. Consume artifacts only under `<executor.root>/.docs/{reqs,plans,tests,done}` with the exact story; include optional test spec only when present. Before manifest creation, copy the exact consumed REQ/AP/optional test/DD artifacts byte-for-byte into immutable `handoffs/{task}/{contract}/rpd-evidence/`, preserving category filenames, and persist `RPD-TERMINAL.md` there. Manifest sources reference only these project-relative snapshots and their hashes, so executor paths never escape the project. Require VR passed, CR pass/fix, matching DD, and command evidence for verified. RPD remains unchanged.

### Deterministic scripts and command routing

- Provide six read-only CLIs: `project-validate.js`, `project-status.js`, `project-next.js`, `project-blocked.js`, `project-coverage.js`, and `project-report-data.js`, sharing `scripts/lib/project-state.js` and `contracts.js`.
- CLI syntax is `node <script> <project-folder> [--json] [--help]`; project folder is mandatory with no default. Unknown/missing/extra args and path/I/O/grammar failures exit `2`; semantic validation failures exit `1`; success exits `0`.
- JSON success envelope is exactly `{ok:true,command,project:{id,root},data}`; failure is exactly `{ok:false,command,project:null|{id,root},errors:[{code,path,message}]}` and never contains data. Every data object begins `schema_version:1`; `valid:false` never appears because semantic invalidity uses the failure envelope/exit 1. Validate data is exactly `{schema_version:1,valid:true,warnings:[{code,path,message}],modules:{milestones,risks,decisions,sources,traceability,changes,handoffs,reports},counts:{tasks,milestones,risks,decisions,sources,changes}}` with module booleans and non-negative integer counts. Status data is exactly `{schema_version:1,as_of_date,project:{status,current_milestone,target_date},tasks:{total,by_status:{planned,ready,in_progress,implemented,verification,verified,done},actionable,blocked},success:{total,covered,verified},milestones:{configured,items:[{id,status,target_date,forecast_date,overdue}]},coverage:{configured,total,covered,verified},risks:{configured,open,high},decisions:{configured,proposed}}`; absent module objects are `{configured:false}` with no extra keys. Next data is `{schema_version:1,tasks:[{id,title,critical,unlocks,priority,milestone,reasons:[strings]}]}`. Blocked data is `{schema_version:1,tasks:[{id,title,dependency_tasks:[task IDs],waiting_on:[explicit-blocker strings]}]}`. Coverage data is `{schema_version:1,configured,criteria:{total,covered,verified,uncovered},items:[{source_id,criterion,tasks,covered,verified}]}`, with zero counts/items only when configured and `{schema_version:1,configured:false}` otherwise. Report-data is `{schema_version:1,status:<status data without schema_version>,risks:{configured,items:[full risk records]}|{configured:false},decisions:{configured,items:[full decision records]}|{configured:false},sources:{configured,items:[full source records]}|{configured:false},changes:{configured,items:[full change records]}|{configured:false},ownership:[{task_id,owner}],blockers:[blocked item],next:[next item],forecasts:[{milestone_id,date,updated,evidence}],unknowns:[{field,reason}]}`. Arrays use stable ID order except ranked next; ownership includes every task and preserves null as an actionable missing owner; unknown fields are dotted names and non-empty reasons. Unknown scalar values are JSON null and appear once in unknowns.
- Next-work considers only active projects and valid ready tasks. Filter explicit/dependency blockers. Rank by `critical:true`, number of tasks that would become dependency-ready if the candidate completed, P0→P3, current-milestone membership, then ID. Call this declared criticality/unlocks, never critical-path scheduling.
- Status/report data includes task distributions, actionable/blocked work, complete task ownership (including null gaps), optional milestone health, optional coverage, open/high risks, proposed decisions, source/change state, and explicit unknowns. A milestone is overdue only when target date is earlier than the captured UTC `as_of_date`; date equality is not overdue. Forecasts are declared with evidence or unknown.
- User routes stay small: `project init <folder> <objective-or-source>`, `project plan <folder>`, `project update <folder> <change-or-evidence>`, `project status <folder>`, `project next <folder>`, `project report <folder> <audience>`, and `project review <folder>`. Report audience is exactly `operator|project-manager|executive|board`; any other or omitted value is rejected before rendering or path construction. Natural language such as “start TASK-X using RPD” coordinates a Task Contract through `project update`; it does not require a large command surface.

### Mutation safety

- Validate live state, copy selected folder to a same-filesystem candidate/backup, change candidate, validate privately, atomically replace target paths, then validate live state; restore bytes/remove new paths on failure. Init accepts a nonexistent target or an existing directory proven empty immediately before apply. For an empty target, rename it to a backup, rename the validated candidate into place, then delete backup; restore the empty directory on failure. Refuse non-empty targets.
- `lstat` every known state directory/file, reject symlinks and unexpected non-regular entries, and require realpaths under the selected root. External source locations are evidence inputs, never writable project-state paths.

## Rollback / Risk

- A flexible Markdown format can become ambiguous. Use one strict collection grammar and fail closed.
- Progressive structure can become incompatible profiles. Keep one schema and add optional modules monotonically; do not create migration modes.
- Evidence can be stale or replayed. Bind immutable contracts/manifests to exact task/source hashes and attempt IDs.
- RPD cannot be required for generic use. Keep the adapter optional and test human execution separately.
- External source files may be inaccessible or change. Record version/hash when available and report unknown/stale instead of inventing certainty.
- Multi-file edits can partially fail. Validate candidates and restore exact prior bytes.
- The new skill is untracked and has no migration; rollback is scoped removal of its files and matching story artifacts.
